# Capability provenance and supported component isolation

Author draft, not a proved result or an accepted planning gate. The normative package is [capability-provenance-isolation](../openspec/changes/capability-provenance-isolation/proposal.md); its [design](../openspec/changes/capability-provenance-isolation/design.md) and [tasks](../openspec/changes/capability-provenance-isolation/tasks.md) are the proposed contract. All implementation tasks remain unchecked.

The existing sequential executor already records actual capability issues, revocations and invocations. The proposed proof follows those initialized prefixes: each final grant comes from an explicitly trusted initial entry or an authorized actual issue, IDs are never reused, revoked entries remain tombstones, and successful uses refer to their current pre-store. Trust in initial grants, the registry, administrators and authenticated boundaries remains a premise.

The proposed isolation result frames observers supported on named ledger cells, exact selected capability lookups and optional nextId. A real issue can change allocation metadata even when no selected existing entry changes. A real revoke can change a store-sensitive predicate while leaving every balance unchanged. Support must include those dependencies.

Catalog validation can exclude a peer's direct read and write access to another component's private cells. That still does not make the entire execution confidential: readable shared state can affect guards, and an owner can publish a snapshot of its private balance through an output port which another component later consumes. The package includes these negative companions. A general confidentiality theorem needs a later disclosure/history/environment policy and relational proof.

This is deliberately separate from new concurrent authority semantics. Current parallel/interleaving branches are lists of invocations and retain the initial store. Concurrent allocation, cross-branch issuance visibility, ID reservation and atomic administrative rollback need their own future design. Existing invocation-only corollaries do not solve those gaps.

The planned executable additions are read-only origin/authority and selected-view queries over actual execution, with fourteen explicitly scoped query/observer mutations. Complete financial expected observations retain raw event before/post worlds as well as final world, full store, receipts, outputs, indices and failures; current cursorEq alone omits past raw worlds. Existing authority mutations and all relevant accepted regressions remain separate evidence.

# P20 delivered API preparation

P20 requires accepted P19 supported-domain correspondence, a nontrivial executable compatibility check on recomputed footprints, and an actual Lean-checked library instantiation. This is a static inventory of delivered dependencies. It does not implement P20, execute a new test, instantiate a theorem for a certificate, or defer the universal proof currently assigned to P19/R8.

Compatibility.lean already supplies the relevant executable path. Parallel.admit validates the decoded catalog, analyzes the entire left branch, analyzes the entire right branch, and calls checkCompatibility. analyzeInvocation resolves required and declared reads, declared writes and delta targets, checks component access, and includes writes and output-port cells among reads. analyzeBranchFrom covers the entire structural suffix, including branches whose financial execution might refuse earlier. The adapter must supply decoded configuration, invocation branches and their explicit boundaries; caller footprint lists are not recomputation.

checkCompatibility deterministically checks write/write, left-write/right-read, then right-write/left-read conflicts. The proof checkCompatibility_ok_iff connects successful executable comparison with the proof-level Compatible proposition. admit_ok additionally supplies catalog validity and both successful branch analyses. Calling or serializing Compatible alone cannot satisfy task21.2.

CompatibilityTests.lean contains independent development controls: exact nonempty USD/share footprints, funded transfer siblings, admitted independent branches, conflicting writes, read conflicts, hidden structural reads and suffix cases. These can inform the adapter's independent literals. Their existence is not a new execution of the future serialized compatibility entrypoint, and the empty-branch cases cannot replace its required nontrivial positive.

For task21.3, Arithmetic.Fees.feeFromGross_conservation is one available real library theorem. It quantifies over rounding mode, a bounded Word, rate numerator/denominator and a FeeQuote, and requires actual feeFromGross success before proving charged.value = received.value + fee.value. Arithmetic.Quantity contains fromRat_ok_iff and toQuantity_fromRat bridges that may be needed when the certificate uses rational amounts. These are possible dependencies, not a selected or implemented certificate adapter. The eventual author must bind actual certificate operands, the concrete instantiated statement and proof term to a recorded compiler check. A matching theorem name, module string or general axiom-audit pass is insufficient.

The existing P16 token0 library is another permitted task21.3 route after its accepted delivery. This inventory does not choose a weaker unrelated theorem solely because it is easy to instantiate. The selected theorem must be used by the certificate example and its checked result.

Before qualified certificate delivery, complete the assigned universal codec/checker correspondence, implement the declared serialized compatibility payload and its real adapter, prove the connection to recomputed footprints, instantiate the selected library theorem for actual decoded data, run independent positive/refusal controls and obtain fresh Grok candidate review. Other future Tree/Claims/Nary/atomic/Quint operators retain their own correspondence obligations. None of this proves deployed-source fidelity or closes P30.

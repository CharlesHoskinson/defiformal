# Cold-reader review

Read only README.md, as a software engineer familiar with ordinary banking but unfamiliar with DeFi and Lean. This is a reader review, not a mathematical acceptance review.

The README gives me a credible purpose and an executable first task. I can explain the basic use: describe balances, permissions, and financial actions; run requests against that model; connect actions into a workflow; use Lean to prove that stated properties survive those connections. I would begin by running the Alice/Bob transfer, then copy and adapt a financial example. I would still need a Lean introduction and a worked modeling walkthrough to build my own component confidently.

1. **Define the subject and tool in the opening.** “DeFi” is never expanded, and “Lean library” assumes familiarity with the main prerequisite. The later sentence about Lean checking mathematical arguments helps, but arrives after several conceptual paragraphs. Suggested opening: “DeFi Kernel is a library for modeling decentralized finance (DeFi): financial services implemented in software, often as blockchain smart contracts. It uses Lean, a programming language and proof assistant, to describe financial operations, run examples, and check proofs about how operations work together.” Keep the precise limit about deployed contracts in the scope section.

2. **Make the motivating composition problem concrete.** The opening explains that operations feed one another but asks an abstract question about “financial properties” before showing an example. A short example would connect the problem to banking knowledge: “A workflow might deposit dollars into a vault, receive shares, and use those shares as collateral for a loan. The kernel models the balances and permissions at each step, including what happens if a later step fails.” Use an example that accurately matches the library's supported models; the README alone does not establish this particular workflow is provided.

3. **The first run is actionable; the first custom model is still a jump.** The commands, starting balances, separate initial states, and insufficient-funds result are unusually clear. In “Model a financial component,” the reader goes directly from this small demo to defining a Template and proving preservation premises. A short concrete task would bridge the gap: identify one named transfer template in the linked file, say which input or condition to change, and explain the expected successful and refused outcomes. Explicitly state that extending the library requires learning Lean. The existing source links are useful, but are not a substitute for that first modification.

4. **Reduce the undefined vocabulary in “How it works.”** “Vault” and “shares” need a brief explanation, such as “a vault holds deposited assets and issues shares recording a depositor's claim.” “Cells” should be “individual ledger or state entries,” or be defined if it includes more. “Ports” can be “named, typed inputs and outputs.” “External observations” would be clearer with “such as a supplied market price.” Later, define “oracle” as the source of a reported external price and “minting or burning” as creating or destroying asset units. Capabilities and domains are already explained well.

5. **Keep theorem language from sounding like an automatic guarantee.** “The proofs connect execution to accounting, authority, and locality” is vague for this reader, while the following discussion of interfaces, invariants, and a frame theorem is dense. Suggested wording: “The library proves accounting and access rules for its execution model. To use a workflow theorem, you must prove its stated conditions, such as compatible access and a property that holds before execution. A property concerning only untouched state can then remain true after the workflow.” The later warning that registering a template does not prove economic correctness is valuable; retaining it prevents a misleading promise.

6. **Move detailed verification machinery out of the main introduction.** The README is readable and free of chronology or hype, but five audit commands plus axioms, mutation tests, verification records, and a broad repository inventory compete with the basic usage path. Keep the runnable transfer, one link to the audit instructions, the core scope limits, and the most useful source locations. Move the distinction between proof/test/mutation evidence and the full tooling inventory to a linked verification guide. This would shorten the page without weakening the central claim. In the execution-mode table, “declared settlement obligations” also needs a concrete definition or a link; ordinary banking familiarity does not explain its exact meaning in this model.

# Cold-reader review: formal-methods researcher / security auditor

Reviewed only README.md, before consulting any implementation or other project files. No builds or source verification were performed. This is reader feedback, not an independent proof audit or native acceptance verdict.

The README stands alone well: its purpose is clear, the runnable example is concrete, and it distinguishes mathematical models, executable checks, and deployed-contract guarantees. It avoids chronology and hype. I would retain that structure and make five targeted changes.

1. **Explain what atomic settlement actually settles.** “Declared settlement obligations are cleared” leaves a security reader unable to tell whether this means debt repayment, balanced net effects, or a user-supplied predicate. Add a short, model-specific definition immediately below the mode table. Suggested wording, subject to checking the actual policy semantics: “An atomic policy identifies settlement lanes and participating principals. The batch tracks signed obligations from executed receipts and commits only when every tracked obligation is zero and the lane supply checks pass. This condition does not establish market solvency.”

2. **Make mode selection an explicit modeling decision.** The table explains behavior, but a reader could select disjoint parallel merely because transfers use different recipients, or assume one scheduled execution covers every possible schedule. Add: “Use sequential execution for one ordered workflow, disjoint parallel when the declared read/write footprints satisfy its compatibility checks, shared-state interleaving to study a particular supplied schedule, and atomic execution when the modeled public boundary requires all-or-nothing publication. A result for one schedule does not by itself cover every schedule.”

3. **Qualify the broad locality sentence.** “Operations can change only the state their permissions and access declarations allow” sounds like one unconditional theorem covering every constructor and every kind of state. Replace with: “Successful invocations enforce the modeled capability and access checks. Preservation theorems specify which ledger and authority properties follow, and under which initial-state and interface assumptions.” This also prompts readers to inspect actual theorem statements rather than infer a universal security guarantee.

4. **Separate semantic assumptions from the verification trust base.** “Authentic … registries … and capability stores” is hard to interpret for an auditor: registries and stores are modeled data, while caller authentication and correspondence to the deployed system are external obligations. Replace with: “Caller contexts, administrator assignments, registry contents, and initial capability stores are explicit model inputs. Applying a theorem to a real system requires showing that these inputs and the modeled execution match that system.” Add: “Proof acceptance also depends on Lean’s kernel and the axioms reported by the verification modules.” The README need not contain a lengthy trusted-computing-base inventory.

5. **Give a direct path from a guarantee to its exact checked statement.** The file map points mostly to broad directories, and “the verification modules” are not linked or invoked explicitly. A first-time auditor needs a named proof and its assumptions before browsing verification records. Add a short linked entry in “Scope of the guarantees”: “To inspect a guarantee, start with [a representative preservation theorem] and [its axiom-audit module]. Read the theorem’s full premises alongside the executable example; the example is not a proof of the general claim.” Replace the placeholders with actual declaration/module links and show the audit command that checks them.

These are clarity and discoverability issues. This read did not establish a false mathematical claim, a broken command, or a missing implementation. The existing warnings about administrator authority versus owner consent, oracle truth, exact arithmetic, net effects, and deployed correspondence are useful and should remain.
